## Overview

The original eBird dataset was converted from compressed TSV into Parquet to support efficient analysis of over 1.35 billion observation records.

The preprocessing pipeline uses Python, indexed gzip access, PyArrow, and DuckDB.

## Processing Pipeline

1. **Extraction:** Used indexed gzip access and parallel processing to read the large source file in chunks.
2. **Column selection:** Retained 30 of the original 52 attributes relevant to the project.
3. **Conversion:** Saved observations into ZSTD-compressed Parquet files.
4. **Validation:** Checked observation identifiers, record counts, and extraction boundaries.
5. **Aggregation:** Used DuckDB to generate state/county and monthly/annual species summaries.

The original compressed dataset was approximately 124.62 GiB, while the resulting Parquet warehouse occupies approximately 62.86 GiB.

## Data Validation

The extraction was checked using the following methods:

- **Record count:** Confirmed 1,350,644,619 records across the Parquet warehouse.
- **Identifier uniqueness:** Confirmed every observation identifier was unique and nonmissing.
- **Boundary validation:** Compared sampled extracted records against the original source to detect missing or duplicated records at chunk boundaries.
- **Aggregation consistency:** Verified that monthly and annual summary totals match.

These checks validate processing consistency but do not establish the scientific accuracy of individual observations.

## Design Decisions

**Parquet storage:** Columnar storage and ZSTD compression reduce storage requirements and support efficient analytical queries.

**DuckDB processing:** DuckDB performs large-scale aggregations directly over Parquet without importing the entire observation warehouse.

**State/county aggregation:** Geographic analysis focuses on state and county identifiers rather than individual observation localities.

**Precomputed summaries:** Monthly and annual results are stored for reuse, avoiding repeated full-data scans during dashboard interactions.

## Portable Massachusetts warehouse: parquet_ma/

The Massachusetts warehouse mirrors the original data layout. All observations are retained in the production files; the three root files expose the same normalized schemas as the original prototypes. Generated data is not committed to Git.

```text
parquet_ma/
  observations.parquet
  locations.parquet
  taxa.parquet
  manifest.json
  validation.json
  production/
    part_00000.parquet ... part_00031.parquet
    part_00000.done.json ... part_00031.done.json
    plan.json
```

The original root Parquet files were generated by `scripts/build_tables.py` from only 100,000 nationwide observations. Filtering those prototypes would provide just 3,657 Massachusetts observations. The new root tables instead derive from all 47,314,166 validated Massachusetts observations. Existing `parquet/production/` and `parquet/massachusetts/` are left untouched. Test exports, locks and scratch directories are not mirrored.

### Dependencies and commands

Python 3.12+ is required; verification used Python 3.13 and the existing pinned DuckDB 2.0.0/PyArrow 26.0.0 dependencies:

```powershell
# Run these commands from the repository root.

```

To reorganize an already validated legacy Massachusetts export, without scanning the 998 nationwide files:

```powershell
py scripts/extract_massachusetts.py --reuse-export parquet/massachusetts --output parquet_ma --prototype-dir parquet --memory-limit 4GB --threads 4
```

This copies the 32 files byte-for-byte into flat `production/part_*.parquet` names. SHA-256 checksums, schemas and row counts must match the old manifest. The old manifest/report are checked for matching successful validation and their hashes/provenance are recorded. Root-table generation and validation read only Massachusetts data and the small prototype schemas, not the nationwide observations. No source files are moved, overwritten, hard-linked or recompressed.

To independently audit the mirrored dataset, optionally also verifying its retained reference export:

```powershell
py scripts/validate_massachusetts.py --dataset parquet_ma --reference-export parquet/massachusetts --memory-limit 4GB --threads 4
```

Omit `--reference-export` to validate the self-contained mirror against its recorded source hashes, production rows and normalization policy; the original directories need not exist. This is an integrity/derivation audit, not a new comparison against the 998 original files. Legacy format-1 audits remain supported with an explicit dataset path:

```powershell
py scripts/validate_massachusetts.py --input parquet/production --dataset parquet/massachusetts --memory-limit 4GB --threads 4
```

That legacy audit intentionally rescans the original snapshot; it is not required for reorganization and was not run for this migration.

For future extraction from a nationwide snapshot, the default layout/output is now `parquet_ma/`:

```powershell
py scripts/extract_massachusetts.py --input parquet/production --output parquet_ma --prototype-dir parquet --batch-size 32 --file-size-mib 256 --memory-limit 4GB --threads 4
```

Without `--reuse-export`, the script first builds and fully validates an internal format-1 observation export under staging, then assembles the mirror. The temporary observation workspace is removed only after the new data validates, and its proof/provenance remains in the new plan. There is no date, category, locality-type, approval-status, name or county restriction: the sole observation filter is authoritative `state_code = 'US-MA'`. The 30-column production schema and every original value/duplicate are preserved. `--layout legacy` remains available explicitly for previous workflows; existing format-1 exports do not need to be converted to remain queryable.

### Publication, resumption and resource limits

All work stays under `parquet_ma.incomplete/` until validation succeeds, then the directory is renamed to `parquet_ma/`. An existing completed destination is always refused. Choose another ignored/external output path for a subsequent build. Both original datasets remain read-only.

Append `--resume` to the same assembly command after interruption. Input/reference fingerprints, prototype schemas and relevant settings must match. Completed observation copies are reused only when hashes/schema/counts match; interrupted or damaged copies are regenerated from the retained reference. Root-table checkpoints are also verified before reuse. No failed validation publishes a new completed dataset. Fresh-extraction resumption retains the prior observation/validation checkpoints and does not restart a completed national extraction simply because publication was interrupted.

Default DuckDB spill storage is `parquet_ma.incomplete/.duckdb_tmp/` and is removed after connections close. `--temp-directory` permits separate scratch outside protected source/output directories. `--memory-limit` and `--threads` may change on resume. DuckDB manages/spills the large relational operations; no whole dataset or pandas frame is loaded into Python. Numeric conversion runs on distinct input strings via the shared prototype helpers. The memory limit governs DuckDB's buffer manager, not every process allocation. Validation needs temporary disk space in addition to the final files.

The existing format-1 extractor still uses bounded source batches, configurable approximate compressed file targets, ZSTD and explicit source-file lists. Subset development mode uses `--max-files` and a separate output path; reports retain a subset flag. Never present a subset test as the full warehouse. Source identity checks use path/size/nanosecond mtime; output checksums use SHA-256. Keep source snapshots immutable while extracting.

An OS lock prevents simultaneous builds/audits of the same destination. Locks live outside the dataset so publication can safely rename it on Windows. Git exclusions cover `parquet/`, `parquet_ma/`, `parquet_ma.incomplete/`, and default lock/audit scratch paths. Custom outputs must also be ignored or outside the repository; never force-add generated Parquet data.

### Exact prototype normalization and catalogs

The root schemas match the original files, including column order and nullability:

- `observations.parquet`: observation_id, checklist_id, taxon_id, locality_id, observation_date, count_raw (strings), observation_count (int64).
- `locations.parquet`: locality_id, locality_name (strings), latitude, longitude (float64), state_code, county_code (strings).
- `taxa.parquet`: taxon_id, common_name, scientific_name, category (strings), taxonomic_order (int64).

The pure functions were extracted to `scripts/prototype_normalization.py` and are also used by `build_tables.py`. Python `int()`/`float()` parsing is retained, including whitespace/Unicode/underscore handling. Invalid counts such as `X` or `1.5` become null integers rather than rounded values. SQLite's NaN-to-NULL and negative-zero-to-zero storage behavior is preserved for coordinates; infinities remain doubles. Out-of-int64 integers fail rather than truncate. Empty taxon/locality IDs become null references and have no catalog entry. Other textual blanks are restored to empty strings as in the prototype; production extraction had encoded those raw TSV blanks as nulls. The copied production observations themselves are never changed.

The prototype has an existing catalog policy: its batch dictionaries retain the last row per ID within a 10,000-row batch, and SQLite `INSERT OR IGNORE` keeps the first inserted batch's choice. The new generator reuses this first-batch/last-row rule, keeping a coherent metadata row. Since the validated export no longer contains original nationwide traversal positions, it applies the rule in deterministic flat-part/file-row order. The policy/order/batch size are recorded in the manifest. It does not use the proposed latest-date fallback because an existing policy was found. Exact historical traversal-dependent choices cannot generally be reconstructed without original ordering; this build has zero normalized catalog conflicts, so that limitation has no effect on its catalog values.

Observation rows deliberately retain all duplicate multiplicities, as required, rather than reproducing the prototype SQLite primary-key deduplication. Catalogs remain unique by locality/taxon ID. There is no prototype 100,000-row limit on these tables.

Conflict reports use normalized catalog metadata and distinguish: IDs with more than one variant, distinct variants at those IDs, excess distinct variants, and the number of observation records carrying metadata different from the selected catalog row. Thus repeated conflicts and distinct conflicting values are not confused.

### Validation and measured warehouse contents

Before publication, validation checks:

- Every production file's bytes/schema/rows against the validated Massachusetts reference; per-file `.done.json` and `production/plan.json` must accurately describe the new mapping, not old gzip offsets.
- No unexpected/missing Parquet files; exact root schemas match the prototypes.
- Production state membership and row/date coverage.
- Full-row bidirectional `EXCEPT ALL` comparisons for each normalized table, preserving duplicates.
- Catalog key uniqueness, all non-null observation-to-location/taxon references, and independently recomputed conflict statistics.
- Final file checksums and unchanged reference-export evidence.

The format-2 manifest records source/reference checksums and the original national validation fingerprint, normalized schemas/policy, copy/table checkpoints and conflict counts. `validation.json` records the new warehouse audit. Source paths are build-time provenance, not Parquet runtime dependencies; a fresh-extraction reference path identifies a removed temporary workspace, while a reused legacy reference is retained externally.

Query either the raw production observations or the normalized observations explicitly; do not glob all Parquet files recursively, which would mix catalogs and count observations twice:

```python
import duckdb

with duckdb.connect() as con:
    print(con.execute("SELECT COUNT(*) FROM read_parquet('parquet_ma/production/part_*.parquet')").fetchone())
    print(con.execute("""
        SELECT COUNT(*)
        FROM read_parquet('parquet_ma/observations.parquet') o
        JOIN read_parquet('parquet_ma/locations.parquet') l USING(locality_id)
        WHERE l.state_code='US-MA'
    """).fetchone())
```

This data reorganization does not switch application API routes or rebuild its serving databases.
